03 / CORE PRINCIPLES

核心不是“新增执行器”，而是影响已有协议输入

① 监听：从报文理解当前状态

根据总线、ID、DLC、MUX 和校验判断帧是否可用，把挡位、车速、座椅位置等变成带时间戳的快照。未见、无效和过期必须分别处理，旧刹车状态不能一直当作有效。

② 仿真操作：把意图翻译为请求

一些报文表示按键、滚轮或挡位请求。固件在条件允许时构造相同协议的请求，尝试让原车控制器按既有流程处理。车辆能否接受，取决于实际状态、协议版本和控制器约束。

③ 局部覆盖：保留模板，只改目标字段

同一帧可能包含多个不相关字段。复制新鲜原车模板，可以保留未知位；再对目标掩码编辑并更新协议计数与校验。同 ID 不同 MUX还可承载不同业务，不能看到 ID 就直接解释整帧。

④ 闭环：输出以后还要看结果

座椅回位比较位置误差，换挡观察实际挡位，预热区分请求与加热。发送服务返回的成功，只是中间证据；若没有匹配的车辆观察链，就不能证明动作完成。

CAN 层面的边界：ID 用于仲裁 / 报文识别，不等于可靠的应用层发送者身份。格式、计数和校验匹配，可能让请求具备被处理的条件，但校验正确不是授权证明，也不保证原车采纳。此项目未证明能压制原节点、取消原帧或实现对所有控制器的“接管”。

一个容易看懂的例子：记忆座椅

保存目标记录四轴位置计数，不是存一张照片。
读取当前位置从反馈帧取得四轴值，检查有效性和时效。
比较与请求依据误差选择方向动作；到达某轴目标就停该轴。
收敛与退出全部到位、物理输入、超时或取消时结算停止。

所以“位置记忆”的原理是 位置反馈 + 方向请求 + 周期比较，不是有一个神奇的“回到记忆槽”固定帧。

04 / EXECUTION LIFECYCLE

从点击按钮到实际效果，中间有四道结果

1 · 管理层接受参数通过或命令排队；可能尚未应用 / 保存。
2 · 输出提交状态机生成候选，发送服务接受并绑定 token。
3 · TX 终态匹配本次 token / generation 的发送处理结果。
4 · 车辆观察新鲜实际反馈符合目标；仍需区分关联与因果。

owner / generation / token

owner：本固件内哪个功能负责某发送流，不是独占物理 CAN。generation：配置、来源或请求的一代；取消后旧代失效。token：某次提交的回执编号，避免把迟到回执算到新动作上。

为什么必须有新鲜模板

复制过期来源可能重放旧状态或错误计数。不同路径时效不同：扭矩来源约 5ms、3C2 合并约 5ms、座椅模板约 500ms、氛围灯模板约 1500ms；不能用统一超时概括。

离线演示 · 为什么“开关打开”仍不输出

以座椅模板 ≤500ms 的门控做简化示意，额外检查已省略；不是原固件模拟器，不生成报文、不连接任何设备。

停止也不是只改一个布尔值：需要阻止未来输出、使旧 generation 失效、处理 pending，再按功能释放 owner 或恢复驱动。OTA 前的 CAN 静默与配置 flush 同理。
05 / FUNCTION MECHANISMS

十组核心功能：输入、决策、请求与确认

01

FSD 与激活

用协议动作请求原车辅助驾驶流程

CH / VEH · 0x3FD、0x3C2

为什么能实现

原车控制器已经有辅助驾驶状态与物理按键输入的处理逻辑。固件观察可用状态和按键、挡位等事件，在允许的阶段构造相应协议动作；它没有在 ESP32 上重新实现感知、规划和整车自动驾驶。

执行链路

  1. 输入：协议 V12/V13/V14、FSD/AP 可用状态、挡位、速度、短按/长按或预警事件。
  2. 决策：可用状态累计确认，筛选已启用事件，检查来源时效与总开关，再进入协议对应阶段。
  3. 输出：跟随 0x3FD 的不同 MUX 与 0x3C2 的按键字段；CH 3FD MUX0 有专门高优先级 P0 路径。
  4. 确认：发送终态与后续状态共同推进，不能以网页开关或 TX 成功代替激活完成。
证据边界 不能把某一组位写成通用“开启 FSD”命令；完整阶段含义、版本差异和全部确认链尚有缺口。

02

速度补偿与驾驶模式

修改原车策略输入中的偏移字段

CH / VEH · 0x3FD MUX2 / MUX0

为什么能实现

车辆已有设速与驾驶策略控制器。固件把驾驶员目标表、原车限速等输入转换为协议里的百分比偏移和模式字段。修改的是策略输入，不是直接设置电机转速，也不能把偏移字节读成 km/h。

执行链路

  1. 输入：限速、原车偏移/智能设速、当前驾驶员、30 格目标表与协议版本。
  2. 决策：选择目标来源，执行限幅、稳定与缓降逻辑，形成有效目标 token。
  3. 输出：V13/V14 偏移为百分比编码；V12 使用四分之一百分比拆位编码；V14 另有五档 profile。
  4. 确认：区分 finalRaw 与 confirmedRaw，失败后从已确认状态恢复。
证据边界 目标优先级、舍入、所有缓降边界及回退确认未完整恢复。

03

扭矩与滚轮免打扰

向提醒判断链提供被修改的输入信号

PARTY · 0x39B / 0x370；VEH · 0x3C2

为什么能实现

相关提醒会利用扭矩、驾驶员状态或输入活动。固件在来源与状态机门控成立时，覆盖扭矩相关输入或模拟滚轮活动，从而尝试影响原车提醒判断。这里的扭矩字段覆盖不能等同于“机械固定方向盘”或已证明的实际转向控制。

执行链路

  1. 输入：0x39B 的 DAS/HOS 原值、0x370 的扭矩/转角、来源时间和配置。
  2. 决策：等待有效 DAS、确认方向，按维护、休息、纠正、验证、故障保持等相位选择输出。
  3. 输出：复制新鲜模板，改动扭矩字段并更新计数和校验；滚轮走另一套动作调度与 3C2 字段合并。
  4. 退出：过期、角度不允许、owner 冲突或 pending 可阻止输出；不是固定周期无条件发送。
证据边界 可能削弱原车驾驶员提醒；完整 HOS 枚举、全部失败恢复链和车辆效果未验证。

04

摄像头与 ISA

状态字段覆盖，不等于关闭硬件

CH / VEH · 0x3FD MUX1；ISA 输出位仍缺证据

为什么能实现

摄像头相关路径在满足配置与 DAS 条件时覆盖 CAN 状态字段。这只能说明协议状态被修改，不能证明摄像头断电、停止采集或所有驾驶员监控均被关闭。ISA 是独立配置与运行路径。

执行链路

  1. 网页主从开关先归一化，运行时继续检查来源和协议条件。
  2. 摄像头路径已定位 3FD MUX1 的局部修改；V14 有延时及 DAS 时效门控。
  3. 功能退出通常停止覆盖，不能推断固件主动把字段恢复为某一固定值。
  4. ISA 配置链存在，但真实输出 ID/MUX/位和完整许可尚未确认。
证据边界 不能把增强 AP 的字段当作 ISA 提示音字段；也不能用静态网页名称证明物理摄像头行为。

自动换挡与障碍建议

输入条件成立后模拟挡位请求

VEH · 0x678 / 0x229；CH · 0x118；PARTY · 0x255 / 0x12B

为什么能实现

原车有挡位请求与实际挡位反馈。固件把方向盘/滚轮等触发或 PARTY 两种建议帧转成 P/R/D 请求，车辆是否接受仍由后续实际挡位验证。这里没有证据表明固件自己进行摄像头识别或计算完整障碍物模型。

执行链路

  1. 输入：实际挡位、新鲜安全信号、请求模板、冷却/次数、方向触发。
  2. 障碍建议要求 255 与 12B 的对应方向组合都有效；仅 P 挡可消费，离开 P 后清缓存。
  3. V13/V14 生成 678 请求，V12 使用 229；两种协议计数和校验不同。
  4. 请求提交后仍等待 CH118 的实际挡位；TX 终态不是换挡完成。
证据边界 完整刹车授权、雷达融合和异常恢复仍有缺口；变量名 bleObstacle 不能作为蓝牙输入的证据。

06

座椅与位置记忆

把位置误差转成方向动作的闭环

通常 VEH · 0x4F3、0x4E2 / 0x4E3

为什么能实现

手动按钮对应座椅方向动作掩码；位置记忆保存四轴位置计数。回位时固件持续比较当前反馈与目标，再决定每个轴向哪个方向移动，到达后清除动作。因此“记忆槽”不是直接发给车辆的一个槽位编号。

执行链路

  1. 手动：按下后网页约每 250ms 续租，最后续租超过 750ms 停止。
  2. 反馈：4E2/4E3 携带四轴 12bit 位置，0xFFF 无效；位置不是已经标定的毫米或角度。
  3. 回位：每 50ms 比较，误差约 ±5 计数内判到达，超过 500 tick 退出。
  4. 输出：基于 4F3 模板写动作掩码；物理座椅输入会取消自动控制，具体仲裁仍需按证据核对。
证据边界 完整物理输入仲裁、车型映射及异常退出仍未全部恢复；网页断开不应被当作可靠停止机制。

07

氛围灯与提示灯效

事件 → 区域目标 → 统一灯光编码

VEH · 0x679

为什么能实现

颜色、亮度和区域 mask 共用一个编码器。FSD 状态、盲区、转向和迎宾事件先计算每个区域的目标，再合并颜色亮度相同的区域进行发送。复杂灯效来自时间变化的目标序列，而不是每种灯效各有一个专用 CAN ID。

执行链路

  1. 输入：驾驶员配置、六区目标、FSD/盲区/转向/迎宾事件。
  2. 决策：计算当前时刻各区域颜色亮度，并处理覆盖关系。
  3. 输出：679 中 RGB、亮度、区域 mask；相同目标合并，模板需符合来源和时效条件。
  4. 灭灯以亮度为零更可靠；不能把模式字段简单写零当作全部分支的停灯语义。
证据边界 六区实车位置、五种迎宾曲线及完整覆盖优先级未校准。

远光、爆闪与后雾灯

模拟开关事件或覆盖灯状态

VEH · 0x3C2 / 0x249 / 0x273 / 0x3E3

为什么能实现

一类路径模拟操作开关的动作，另一类路径覆盖状态电平。爆闪由状态机交替生成请求和释放，并处理模板和发送结算；不能把开关事件 bit 一直保持为 1 就解释为持续开灯。

执行链路

  1. 远光：非 V12 走 3C2 的 MUX1；V12 走 249 请求并重算校验。
  2. 雾灯：273 的状态覆盖与 3C2 的开关动作并存。
  3. 反馈：3E3 观察灯状态，倒车/减速条件影响调度。
  4. 多个功能共用 3C2 时需字段合并和 owner 仲裁，避免相互覆盖。
证据边界 倒车双闪字段、全部脉冲波形、爆闪次数为零的退出规则和仲裁全序仍有缺口。

电池预热与维修

提出原车服务请求，而非直接驱动执行器

VEH · 0x82 / 0x339

为什么能实现

固件通过车辆已有请求接口表达预热或维修模式意图，车辆热管理或服务逻辑负责是否执行。预热时长由固件计时，到期提出停止；不是把“30 分钟”直接放进一个请求字节。

执行链路

  1. 预热：输入许可和时长，运行状态机提出启动请求，并观察电气、温度及状态帧。
  2. 重试/停止：有 owner、pending、generation 与超时，不能仅重复发送常量。
  3. 维修：339 中存在开关请求构造器，但未恢复完整厂家诊断服务。
  4. 结果：请求被提交、发出、计时启动和电池实际加热是不同层次。
证据边界 实际加热与停止确认信号的全部语义、完整厂家维修流程未恢复。

退出 FSD 后泊车与驾驶位模拟

状态边沿触发请求；两条路径分别控制

CH · 0x399 / 0x257 / 0x293；PARTY · 0x30A；VEH · 0x3A1

为什么能实现

泊车路径观察 FSD 状态变化，在延时、请求窗口和静止条件成立时，利用原车模板提出请求。驾驶位模拟是独立路径，覆盖占用/安全带相关输入，并观察另一条反馈。两者不是一个“离车自动泊车完成”闭环。

执行链路

  1. 泊车：399 退出边沿触发，默认延迟 2 秒、请求窗口 30 秒，还要求两帧新鲜静止信号。
  2. 输出：CH293 的阶段请求；发送前复检当前窗口与状态，移动会暂停输出但计时继续。

bool edit_gear_v12(uint8_t *d, int dlc, int target) {
    if (dlc != 3 && dlc != 8) return false;

    else if (target == 4) { code=4; park=0; }
