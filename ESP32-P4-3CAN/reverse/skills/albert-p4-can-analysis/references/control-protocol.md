## 1. 哪一路 CAN

| 网页线路 / 控制器 | 固件逻辑名 | 内部 bus mask | 网页连接器针脚标签 | A 线序 GPIO TX / RX | B 线序 GPIO TX / RX |
|---|---|---|---|---|---|
| CAN0 / TWAI0 | CH | `1` | `13 / 14` | `2 / 3` | `3 / 2` |
| CAN1 / TWAI1 | VEH | `2` | `9 / 10` | `4 / 5` | `50 / 49` |
| CAN2 / TWAI2 | PARTY | `4` | `2 / 3` | `26 / 27` | `31 / 30` |

三路均为 **500 kbit/s**。GPIO 与连接器针脚是两种编号；连接器数字是原网页标签，尚未做实物线束校准。控制器索引 `0/1/2` 与 bus mask `1/2/4` 分开使用。来源备注：针脚表`0x48222610`、通道表`0x48222640`与setup`0x48117336`；相关探测逻辑见[总线与线序](can-runtime.md)。

记号：`d0…d7` 是 payload 从零开始的字节；`bit0` 最低位；`d5[7:6]` 是 d5 的高两位；ID 和 payload 常量为十六进制，未带 `0x` 的普通数值/时限默认十进制。RX 是接收观察，TX 是构造/发送请求，RX→TX 是复制原车模板后发送同 ID。

**反编译对象不可混用**：普通 Frame 的 ID 在 `+0`、DLC 在 `+4`、payload 在 `+5…+12`、bus mask 在 `+13`；`0x480C4194/0x4804A006` 的 14 字节动作对象把 bus 放 `+5`，payload 放 `+6…+13`。下文全部已换算成 payload 字节号。

## 3. 座椅：哪一个 bit 控制哪个方向

来源/输出 `0x4F3`，DLC=3或4。网页默认 `seatControlBus=2`，标签明确 `CAN1 · VEH / TWAI1`；后端配置值`1`选择CH，其余有效值走VEH；流识别没有PARTY座椅分支。

构造器将动作掩码写为 `d0=mask&255; d1=mask>>8; d2=mask>>16`。DLC=4时d3保留来源值。手动命令要求24bit范围内恰好一个bit，记忆回位可以合并多个轴的方向。

| 动作 | 左座椅掩码 | 左字节/位 | 右座椅掩码 | 右字节/位 |
|---|---|---|---|---|
| 轨道向前 | `0x000004` | d0 bit2 | `0x000001` | d0 bit0 |
| 轨道向后 | `0x000008` | d0 bit3 | `0x000002` | d0 bit1 |
| 靠背前倾 | `0x000080` | d0 bit7 | `0x000020` | d0 bit5 |
| 靠背后仰 | `0x000040` | d0 bit6 | `0x000010` | d0 bit4 |
| 整体升高 | `0x004000` | d1 bit6 | `0x001000` | d1 bit4 |
| 整体降低 | `0x008000` | d1 bit7 | `0x002000` | d1 bit5 |
| 坐垫抬高 | `0x000400` | d1 bit2 | `0x000100` | d1 bit0 |
| 坐垫降低 | `0x000800` | d1 bit3 | `0x000200` | d1 bit1 |
| 腰托向上 | `0x010000` | d2 bit0 | `0x040000` | d2 bit2 |
| 腰托向下 | `0x020000` | d2 bit1 | `0x080000` | d2 bit3 |
| 腰托向内 | `0x100000` | d2 bit4 | `0x400000` | d2 bit6 |
| 腰托向外 | `0x200000` | d2 bit5 | `0x800000` | d2 bit7 |
| 停止全部方向 | `0x000000` | d0..d2=`00 00 00` | 同左 | 同左 |

例：左轨道向前前三字节=`04 00 00`；左升高=`00 40 00`；右腰托向外=`00 00 80`。方向名称来自原网页24个按钮，掩码在C运行命令与构造器中对应使用。

手动控制网页约每250ms续租 `manual_start`；固件最多每50ms提交一次；最后续租超过750ms停止。模板≤500ms、bus匹配、座椅许可、发送许可及无pending是实际门控。物理`0x4F3`非零动作会取消固件自动控制；近100ms自回波另作排除。

<a id="seat-feedback"></a>
### 四轴位置与记忆回位

所选bus的 `0x4E2` 进入side0，`0x4E3`进入side1；左右与上表方向掩码在回位器中配套使用。`d0&7=5`且DLC≥7时按低bit先行提取：

| 轴 / JSON名称 | 全帧起始bit | payload布局 | 原值范围 |
|---|---|---|---|
| 轨道 / `track` | 3 | d0[7:3] + d1[6:0] | 0..4094；4095无效 |
| 靠背 / `backrest` | 16 | d2 + d3[3:0] | 同上 |
| 升降 / `lift` | 28 | d3[7:4] + d4 | 同上 |
| 坐垫 / `tilt` | 40 | d5 + d6[3:0] | 同上 |

这些是位置计数，尚未恢复毫米/角度标定。记忆存储四轴原值；调用槽位后逐轴比较反馈与目标，误差在±5内视为到达；每50ms评估，超过500个tick退出。**没有直接向CAN发送“记忆槽1/2/3”**，而是闭环生成上表方向掩码。

```c
bool build_seat(Frame source, uint32_t mask, Frame *out) {
    if (source.id != 0x4F3 || (source.dlc != 3 && source.dlc != 4)) return false;
    if (!selected_seat_bus(source.bus) || source.age_ms > 500) return false;
    if (!seat_gates_allow(mask) || pending_tx()) return false;
    *out = source;
    for (int i=0; i<3; ++i) out->d[i] = (mask >> (8*i)) & 0xFF;
    return true;
}
bool decode_position(Frame f, uint16_t p[4]) {
    if (f.dlc < 7 || (f.d[0] & 7) != 5) return false;
    int start[4] = {3,16,28,40};
    for (int axis=0; axis<4; ++axis) {
        p[axis] = read_bits_lsb_first(f.d, start[axis], 12);
        if (p[axis] == 0xFFF) return false;
    }
    return true;
}
// 记忆回位：每50ms，从位置误差选择正/负方向；轴到达则清该轴。
// 无来源、物理请求、取消、超时或目标全部到达：请求mask=0并结算停止。
```

证据：手动命令 `0x480E8070`、调度/租约 `0x4810B9CE`、构造 `0x4810B866`、反馈入口（`0x480E1B1C`）、12bit提取（`0x4805625C`）、回位器（`0x4805637A`）。轴名由序列化器（`0x48052FFE`）及镜像`0x481C61E0="lift"/0x481C61E8="tilt"`核对。

<a id="gear"></a>
## 4. 换挡：请求值与实际挡位分别编码

### V13/V14：VEH 0x678，DLC7

来源需通过 `d0 == (0x7E + sum(d1..d6)) & 255` 且 `d1<0x10`，即原车当前没有高半字节请求；模板复制后修改：

```c
bool edit_gear_v13_v14(uint8_t d[7], int target) {
    if (target != 1 && target != 2 && target != 4) return false;
    if (d[1] >= 0x10 || d[0] != sum8(d+1, 6, 0x7E)) return false;
    d[1] = (target << 4) | ((d[1] + 1) & 0x0F);
    d[0] = sum8(d+1, 6, 0x7E);
    return true; // d2..d6保持来源值。
}
```

| 请求 | 传入target | d1高4bit | d1实际值 |
|---|---|---|---|
| P | 1 | `0x10` | `0x10 \| 新counter` |
| R | 2 | `0x20` | `0x20 \| 新counter` |
| D | 4 | `0x40` | `0x40 \| 新counter` |

本生成器不接受target=3，不能把实际挡位的N枚举套用为可发送N命令。counter=`(来源d1低4bit+1)&15`；没有一个可脱离来源的固定d0值。

### V12：VEH 0x229，DLC3或8

来源ID由观察器确认，模板缓存与生成器配套；d0为两张表的XOR校验：

```c
const uint8_t gear_table[8] = {0x00,0xE0,0xEF,0x0F,0xF1,0xE9,0x00,0x00};
const uint8_t count_table[16] = {
  0x46,0x44,0x52,0x6D,0x43,0x41,0xDD,0xF9,
  0x4C,0xA5,0xF6,0x8C,0x49,0x2F,0x31,0x3B
};
bool edit_gear_v12(uint8_t *d, int dlc, int target) {
    if (dlc != 3 && dlc != 8) return false;
    if (d[0] != (gear_table[(d[1]>>4)&7] ^ count_table[d[1]&15])) return false;
    int code, park;
    if (target == 1) { code=0; park=1; }
    else if (target == 2) { code=2; park=0; }
    else if (target == 4) { code=4; park=0; }
    else return false;
    int c = (d[1]+1)&15;
    d[0] = gear_table[code] ^ count_table[c];
    d[1] = (d[1]&0x80) | (code<<4) | c;
    d[2] = (d[2]&0xFC) | park;
    return true;
}
```

表在镜像 `0x48222CA8/0x48222CB0`。这里只替换相应请求/计数位，DLC8的d3..d7保留。

### 门控和反馈

实际挡位来自CH `0x118` 的 `d2>>5`，有效范围1..4；代码明确用P=1、R=2、D=4分支。生成前要有≤300ms的挡位、必要安全信号和模板，模板观察累计至少5帧；还检查通信/VEH TX、runtime所有者、冷却、挡位变化、协议及启用来源。刹车授权、安全带、转角等随配置启用，不可忽略整个外层状态机。确认看后续实际挡位，不把TX终态当成换挡完成。

证据：总生成器 `0x4809E23A`、非V12位运算（`0x480499C2`）、V12位运算（`0x48049A54`）、VEH678来源（`0x481084C2`）、VEH229来源/缓存（`0x48105D3A`）。`0x48109D5A/0x48109298`调用229观察器，缓存对象以主对象`+0x7CD0`为基址，`+0x120`模板对应生成器读的`+0x7DF0`。

<a id="obstacle"></a>
### PARTY 障碍建议是输入，实际换挡仍走上面的生成器

| `0x255 d3&3` | `0x12B (d2>>4)&7` | 专用匹配结果 | 请求挡位 |
|---|---|---|---|
| 1 | 3 | 建议1 / 前进 | D / target4 |
| 2 | 2 | 建议2 / 后退 | R / target2 |
| 其他组合 | 任意 | 不形成该项有效匹配 | 不请求 |

两类帧均要求PARTY、DLC恰为4、来源≤300ms且seen/valid/generation符合条件；仅P挡可消费，离P清缓存，重新回P需两类新帧。转角确认开关与共同换挡门控再筛选建议。公共观察器另读 `0x12B d2>>6` 和 `0x255 (d3>>2)&31`，它们不能替代这里的专用匹配。

证据：专用解析/匹配 `0x4810AB0A`、建议转挡位（`0x48049BB6`）、专用来源缓存（`0x480C7974`）。

<a id="3fd"></a>
## 5. 0x3FD：同一个 ID 按 MUX 控制不同功能

CH/VEH，DLC8，MUX=`d0&7`。字段构造器同样接受两条线路；CH MUX0另由`fsd_p0`高优先级处理，当前来源预算2000µs。策略由配置、DAS状态、来源时间、generation、阶段和发送许可共同决定，不能拿某一位的修改结果替代整个功能。

### MUX1：摄像头屏蔽、增强 AP

| 功能 | 开关/策略来源 | 实际输出字段 | 写入值与边界 |
|---|---|---|---|
| 摄像头屏蔽 | `dndEnabled && cabinCameraDisableEnabled`，再过DAS门控 | d5 bit3 | 清0：`d5 &= 0xF7`；功能退出停止覆盖，不等于主动设回1 |
| 增强AP兼容 | `enhancedAutopilotEnabled` | d2 bit3 | 清0；V14再`d5 |= 0x80` |

V14摄像头覆盖要求有效DAS来源≤1000ms，延时参数归一化3..10秒且到期；完整退出/回退边沿仍需继续恢复。这里的“屏蔽”是固件CAN状态覆盖，不是电气断电证据。

命名核对：配置序列化（`0x4808F6E8`）：cfg`+0x2A=isaChimeSuppressEnabled`、`+0x2B=enhancedAutopilotEnabled`、`+0x2C=cabinCameraDisableEnabled`。策略生成器（`0x4809EC88`）实际用`+0x2B`产生增强AP标志，因此**d2 bit3不能误写成ISA抑制位**。

<a id="speed"></a>
### MUX2速度偏移、MUX0策略、MUX2 V14模式

```c
// 已通过有效目标token/期限检查后，对复制的3FD MUX2模板写入。
void edit_speed_offset(uint8_t d[8], bool v12, uint8_t raw) {
    if (v12) {
        d[0] = (d[0]&0x3F) | ((raw&3)<<6);
        d[1] = (d[1]&0xC0) | (raw>>2);
    } else {
        d[1] = (d[1]&0xC0) | min(raw,60);
    }
}
void edit_v14_profile(uint8_t d[8], unsigned profile) {
    if (profile > 4) profile=2;
    d[7] = (d[7]&0x8F) | (profile<<4);
}
void edit_hw3_strategy(uint8_t d[8], unsigned code) {
    d[6] = (d[6]&0xF9) | (min(code,2)<<1); // MUX0
}
```

V12 raw以0.25%为单位，例如10%→raw40→d0高2bit=`00`、d1低6bit=`0A`；10.25%→raw41→d0高2bit=`40`、d1低6bit仍`0A`。V13/V14的10%→d1低6bit=`0A`。这里raw指CAN字段，配置对象中带Raw的参数可能使用另一种内部单位，不能把配置数值直接塞进payload。这些是百分比偏移，不能把d1直接解释为km/h设速值；目标km/h先由限速、模板、模式、限幅、缓降和优先级算法转为偏移。

HW3手动配置`0=舒适 / 1=标准 / 2=迅捷`，策略生成器映射raw `0/1/2`，写入d6掩码`0x06`；兼容值3也归raw2。自动策略从观察结果产生，实际生效仍受速度/FSD策略门控。

V14 mode `0/1/2/3/4`来自原网页五项枚举，写入d7的`0x70`范围；非法值回2（Hurry）。手动模式开关决定策略来源，协议构造器在速度功能相应分支应用mode；不能仅保存mode就断言车辆已切换。原网页自动车距映射为`1→Max、2→Hurry、3→Normal、4→Chill、5→Sloth`。

### FSD和P挡出发：已恢复的位操作，尚未恢复完整阶段含义

| 帧 | 已确认运算 | 可以得出的结论 |
|---|---|---|
| CH3FD MUX0 | 按阶段 `d5 |= 0x40`、`0x50`或`0x10` | FSD状态机生成不同阶段字段，不能合并成“固定启动帧” |
| CH3FD MUX0 P挡阶段 | `d5 |= 0x82; d6 |= 0x08` | 出发阶段叠加bit1/7及d6 bit3，来源其他位保留 |
| CH3FD MUX2出发阶段 | `d0 |= 0xC0; d7 |= 0x80` | 阶段覆盖，不能与普通偏移raw拆分混写 |
| 3FD MUX0稳盘条件 | `d5 &= 0xFC`；非V14分支清d7 bit4 | 对应策略条件成立时覆盖，完整厂家语义未确认 |
| V14 3FD MUX0 | 按eligible条件清/设d7 bit4 | 原始位运算已确认，厂家字段名未确认，不能叫ISA位 |
| VEH3C2 MUX1按键动作 | d1[5:4]写阶段值1或2 | FSD按键模拟；物理右短按观察识别`d1&0x30==0x20`，全部按下/释放时序待确认 |

<a id="3c2"></a>
## 6. VEH 0x3C2 MUX1：按键、滚轮、远光合并

普通帧DLC8，`d0&3=1`。合并器要求来源≤5000µs、generation匹配，复制原车帧后只修改已有候选的字段组：

| 字段组 | payload范围 | 值/用途 |
|---|---|---|
| A | d1[5:4] | 按键阶段动作，FSD生成值1/2 |
| B | d2[5:0]、d3[5:0]、d6 bit4 | 左/右滚轮signed6动作及释放/动作状态 |
| C | d5[7:6] | 远光相关请求；候选选择顺序为内部`+0x64 > +0x54 > +0x44 > +0x34` |

**d2低6bit是左滚轮，d3低6bit是右滚轮**。字段按6bit补码解释：`0x00=0`、`0x01=+1`、`0x3F=-1`；范围−32..31。输入解析中d2正/负对应cfg`0x7B/0x7C`（左正/负动作），d3对应`0x7D/0x7E`（右正/负动作），与配置字段名（`0x4808F6E8`）交叉核对。输出保留d2/d3高2bit。

调度器的选中滚轮值为0时d6 bit4置1，否则置0；该位完整厂家名称未恢复。网页`dndScrollMode=0`左音量、`1`右速度，运行调度器使用内部选择值1/2，不能直接把页面mode当成CAN字节。全部波形以滚轮调度器（`0x48047F16`）及配置模式为准，不把某个固定+1值写成适用于所有免打扰模式。

```c
signed int signed6(uint8_t x) { x &= 63; return (x&32) ? x-64 : x; }
void merge_scroll(uint8_t d[8], int a, int b, bool release) {
    d[2] = (d[2]&0xC0) | (a&0x3F);
    d[3] = (d[3]&0xC0) | (b&0x3F);
    d[6] = (d[6]&0xEF) | (release ? 0x10 : 0);
}
```

证据：合并器 `0x4804132A`、signed6观察（`0x48105D3A`）、滚轮输出（`0x480CC0A2`）、缓存/合并调用（`0x48109298`）。

<a id="high-beam"></a>
### 远光请求、释放与爆闪

非V12的构造器在来源d5 bit6为0时，写 `d5=(d5&0x3F)|(request<<7)`；request=1输出高两位`10`即`0x80`，request=0输出`00`。它模拟远光输入请求，物理灯是否亮还受车辆控制器条件影响。

V12使用VEH `0x249` DLC4：d1 bit7保留、低4bitcounter+1、d1[6:4]写request (`0/1`)；d0=`table249[request] XOR counter249[counter]`。镜像表：

```c
const uint8_t table249[8] = {0x00,0x76,0xEC,0x00,0xF7,0x00,0x00,0x00};
const uint8_t counter249[16] = {
  0x9B,0xE8,0x2A,0xD3,0xD3,0x83,0x4C,0x5E,
  0x3F,0x5E,0xE2,0x28,0x3A,0x13,0xAF,0xCE
};
// 验证来源校验且d1&0x60==0后：
counter=(source.d1+1)&15;
d1=(source.d1&0x80)|(request<<4)|counter;
d0=table249[request]^counter249[counter]; // d2,d3保留
```

配置`fsdForceHighPhysicalEnabled/longPressHighBeamStrobeEnabled`经`0x480DDA04`写入同一灯光状态对象，调度`0x4804BB9A`再调用`0x4804A56E→0x4804A006`；爆闪在这个状态机中交替生成request/释放。间隔参数C归一化1..100ms，次数0..20，网页默认45ms/0；次数0的完整持续退出语义及全部仲裁优先级尚未恢复。输出不能按网页间隔无条件循环发送，仍要等新鲜模板与在途结算。

证据：配置应用（`0x480DDA04`）、灯光阶段/爆闪（`0x4804BB9A`）、动作准备（`0x4804A56E`）、报文编辑（`0x4804A006`）、物理来源观察（`0x480C4194`）。该编辑器使用payload从`+6`开始的压缩对象，d5对应对象`+11`。

## 7. 氛围灯：VEH 0x679，DLC7

| 内容 | 位置 | 数值/编码 |
|---|---|---|
| 自定义工作模式 | d0[2:1] | 常用`01`，即`(source.d0&1)|0x02` |
| 红/绿/蓝 | d1 / d2 / d3 | 各0..255 |
| 亮度 | d4[6:0] | 0..100；bit7保留 |
| 区域0..4 | d5[7:3] | 6bit区域mask的低5bit左移3 |
| 区域5 | d6 bit0 | 区域mask bit5 |

mask=`1<<区域号`，区域0..5；例如区域0=`d5高5bit=08,d6bit0=0`，区域5=`d5高5bit=00,d6bit0=1`，全部六区mask`0x3F`→d5高5bit`F8`、d6bit0`1`。d5低3bit、d6其余位保留。代码把0..3作为door、4..5作为dash类别；六区的实车具体左右/前后部位未校准。

模板观察器只接收VEH679/DLC7且原区域mask为`0x3F`，要求`d0&6 != 6`、亮度≤100、来源代数有效并排除自发元数据；发送器要求模板≤1500ms。相同RGB/亮度的目标区域会合并mask，避免每个区域都单独发一帧。

```c
void edit_ambient(uint8_t d[7], RGB c, int brightness, uint8_t zones) {
    d[0] = (d[0]&1)|0x02;
    d[1]=c.r; d[2]=c.g; d[3]=c.b;
    d[4]=(d[4]&0x80)|clamp(brightness,0,100);
    d[5]=(d[5]&7)|((zones&31)<<3);
    d[6]=(d[6]&0xFE)|((zones>>5)&1);
}
```

盲区覆盖已确认RGB=`FF 00 00`；转向提示用配置RGB，闪烁灭阶段brightness=0。迎宾五种style由逐帧目标计算器产生RGB/亮度，再走同一个679编码。禁用区域的底层构造器清模式位并写亮度0，但外层自定义/灯效发送分支可能再次强制模式`01`；因此可靠的“灭”值是亮度0，不能把最终d0一概写0。

证据：来源观察 `0x480CCF42`、输出调度（`0x4809FAA6`）、模板/时效/合并（`0x48044258`）、区域编码/覆盖（`0x48043EC8`）、迎宾计算（`0x48042696`）。

## 8. 后雾灯：电平覆盖和开关事件两条路径

| 路径 | 线路/ID | 修改 | 控制方式 |
|---|---|---|---|
| 模板电平覆盖 | VEH273，DLC8 | `d2=(d2&0x7F)|(on?0x80:0)` | 减速、倒车常亮、脉冲阶段等决定on；其他位保留 |

## 9. 电池预热：VEH 0x82，DLC8

| 动作 | d0 d1 d2 d3 d4 d5 d6 d7 |
|---|---|
| 开启请求 | `AF 50 A8 80 FF 03 00 80` |
| 关闭/停止/恢复请求 | `01 50 A8 80 FF 03 00 80` |

这是两组完整固件常量，地址`0x48223DC0/0x48223DC8`；d0的两种值明确，不能凭常量进一步把其余bit命名为厂家完整热管理信号。

名称链：网页`batteryPreheatEnabled/DurationMin`→运行命令`0x480E8070`的主对象`+0x8845/+0x8846`→预热对象主`+0x8820`（实时子对象`+0x378`）→发送器读子对象`+0x39D/+0x39E`。快照`0x48052B10`读取同对象`+0x25/+0x26`，配置序列化器输出预热字段。不是仅凭`0x82`猜功能名称。

最多约每500ms准备一轮请求，受到许可、owner、pending、generation以及10秒动作超时约束。计时从运行状态确认的起点记录；duration按分钟乘60000，到期切换关闭请求与新代数，仍需结算停止/恢复。网页选项15/30/45/60分钟是UI配置，不是写进82的一个“分钟字节”。

预热观察器要求VEH、DLC≥8：`0x2E1`要求`d0&7=0`并观察全帧bit63；`0x132`读电气量计算功率；`0x292`读10bit量；`0x312`读三个9bit温度原值再用`raw*25-2500`转换内部单位。这些观察用于状态/许可，不把“已收到反馈帧”直接等同于电池已在加热；全部实际加热/停止确认字段尚未恢复。

```c
tick_preheat() {
    if (confirmed_timer_running && elapsed_ms >= duration_min*60000)
        intent = STOP, renew_request_generation();
    if (!runtime_allowed || pending_tx || !retry_due) return;
    Frame f = { .bus=VEH, .id=0x82, .dlc=8 };
    copy(f.d, intent==START ? preheat_on : preheat_off, 8);
    validate_request_and_generation_then_submit(f);
    // 提交接受、TX终态、观察反馈、计时起点与恢复分别推进。
}
```

证据：运行命令（`0x480E8070`）、构造/定时（`0x4810BB96`）、预提交校验（`0x48053DE0`）、CAN观察（`0x480524AA`）、快照（`0x48052B10`）、配置输出（`0x48111134`）。

## 11. 退出FSD后的泊车请求与驾驶位模拟

两条路径使用独立开关，默认关闭。泊车由CH399 `d0&0xF` 从3～6进入1/2触发，状态观察间隔≤1500ms；默认延迟2000ms、请求窗口30000ms。FSD总开关、泊车开关、通信、CH TX有效，399仍为1/2且年龄≤1500ms，CH257 `raw=(d6<<5)|(d5>>3)` 连续两帧raw500且间隔／年龄≤100ms时，随CH293构造：

```c
out = src;
out.d[3] = (src.d[3] & 0x0F) | 0xC0;
out.d[6] = (src.d[6] & 0x0F) | (((src.d[6] & 0xF0) + 0x10) & 0xF0);
out.d[7] = (0x95 + sum(out.d[0..6])) & 0xFF;
```

293 DLC8，来源d3高四位已为C则跳过。来源+20000µs截止，stream19在发送前复检相同窗口、状态和速度。移动暂停请求但倒计时继续，到期停止覆盖；未发现专用取消泊车payload。参数虽名v13，所查路径无显式协议13限制。399边沿更新可从错误校验／非8字节分支到达，293构造器无局部来源校验检查，不能补写不存在的严格来源门控。

驾驶位模拟要求独立开关、通信、PARTY TX与传输许可，跟随PARTY30A DLC8且seed0D来源校验合格的报文；无局部FSD总开关、泊车窗口、零车速或关门限制：

```c
out = src;
out.d[0] = (src.d[0] & 0xE0) | 0x09; // 有人值1，安全带值1
out.d[6] = (src.d[6] & 0x0F) | (((src.d[6] & 0xF0) + 0x10) & 0xF0);
out.d[7] = (0x0D + sum(out.d[0..6])) & 0xFF;
```

来源+5000µs截止，stream8。原值已满足、计数重复或pending时跳过。只读VEH3A1，MUX2、seedC0校验合格且上表占用／带状态连续两帧满足才累计采纳确认；间隔与年龄≤300ms。内部TX标志由终态更新；公开Active由0x4805ABF4要求开关启用、成功TX和连续两帧3A1目标反馈均≤300ms。仍不能证明反馈由模拟造成或泊车完成。自动换挡读取构造前的PARTY30A输入缓存，上游自回波剔除尚未全部确认。

来源定位：399解析`0x480D8F08`、速度观察`0x480DA2A8`、293构造`0x480C76A2`、发送前验证`0x480C6318`、30A构造`0x480CB95C`、3A1反馈`0x480CCF42`。完整时序与证据边界见[离车泊车参考](exit-parking.md)。所查路径没有开门／离座触发或车门关闭模拟，原车继续泊车与完成效果未实测。
