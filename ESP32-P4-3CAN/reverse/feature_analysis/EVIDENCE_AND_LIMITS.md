# 证据层次、动态功能与尚未恢复的细节

本次以原始前端为功能清单起点，再核对87条HTTP注册、handler、公共配置、运行调用与状态快照。工作范围是静态分析；原始文件未修改，没有设备交互、云端配置写入或烧录。

协议字段已有进一步补充，优先读[CAN线路/ID/控制值文档](../skills/albert-p4-can-analysis/references/control-protocol.md)。原逐项文档中的“位布局未恢复”是初次整理时的边界；座椅、换挡、摄像头、速度/profile、灯光、预热和维修以该补充的具体字段与缺口为准。原前端资源和自动覆盖清单保持原样。

## 如何理解每项结论

| 证据 | 可确认什么 | 不能直接推导什么 |
|---|---|---|
| HTML控件、CSS、内联事件 | 标签、输入类型、静态范围、初始隐藏与用户入口 | 实际车控效果、服务端授权 |
| JS函数、请求参数与回读 | 单位转换、接口选择、草稿/版本处理、结果展示 | 最终CAN位布局和车辆是否接受 |
| HTTP注册及handler | 方法、真实入口地址、参数解析、错误分支 | 接口返回ok即动作完成 |
| C运行函数、来源检查、发送确认 | 部分状态转换、门控、来源新鲜与终态处理 | 有缺失解码/间接调用的完整算法 |
| 运行诊断字段 | 固件管理的相位、计数、来源及确认状态 | 单凭字段名称恢复全部转换条件 |
| 字符串与交叉引用 | 某字段解析/序列化、错误码和功能关联 | 只有字符串就断言功能已接入运行 |

每项“接口确认；运行语义重建”表示接口有直接证据，而该项伪代码经过抽象整理。`request_activation()`、`gates_pass()`、`compose_target()`等是分析者取的语义名，没有声称恢复了原项目同名函数。

## 动态生成的功能如何覆盖

静态dashboard提取325个控件，login3个。JS的52个可提取HTML片段中得到109行控件，合计437行。该解析不会执行JS，不将固件管理页加载到真实设备上。

以下循环／运行态控件通过生成函数及数据属性覆盖：

- CAN实验：规则可增加至4条，每条最多3lane；8字节逐位match/edit按钮由模板循环生成，按掩码逻辑分析，重复实例不单独当成功能。
- CAN实验：checksum参与字节、预设8槽、来源/输出/每lane统计均由动态数据驱动。
- 驾驶员：列表卡片、选择/改名/删除/重绑定、每个驾驶员的功能开关；实际实例数依存储而变化。
- 速度：5～150km/h的30格模板与V13八段编辑；相同协议算法的重复输入归入模板功能。
- 氛围灯：区域图、编辑器、六区enable、迎宾区域mask与状态。
- FSD记录：范围切换、历史列表、详情与重置/清空dialog。
- 云端：restore scopes、冲突列表动作、引导、设备ID和开发者解锁dialog。
- 诊断：任务明细、各功能运行状态、热点ID、Web指标与崩溃摘要。

控件归属依据区分显式ID、内联事件、data属性、模板函数与HTML语义区域。“437/437归属”是清单检查结果，不是437条运行调用链全部逐指令证明。

## 地址与反编译限制

原固件Arduino/ESP-IDF代码为C++，导出采用C表达。4,966个函数中1,267份有推断警告，119份包含坏指令／坏函数标记，13份存在未确定寄存器值，统计类别可重叠。

直接调用表未列出虚函数、函数指针等间接调用，自动发现也会漏建函数。补充 CAN 分析在反汇编中发现未建入口`0x480c5306`：它检查PARTY mask4、DLC=8与ID39B/370，并在`0x480c5616`直接调用`0x4804ea2a`，随后在`0x480c5874`调用专用来源跟随提交`0x480459fe`。calls.tsv没有这个caller，不能据此判断扭矩未接入。详见[新增CAN证据](../skills/albert-p4-can-analysis/references/evidence.md)。模块“关联函数”表示已核对的语义入口／辅助，不代表每个功能都直接调用全部列表；部分模板辅助亦被多种业务共用。

ROM/libgcc标注使用与P4 revision≥3匹配的ESP-IDF v5.5.5 ECO5表。文档未引入旧ROM映射。所有地址为原固件虚拟地址，重新编译后的函数地址会改变。
